Does Z.ai's own endpoint serve glm-5.3-flash, and does its effort dial bind? - 2026-09-12

VERDICT: FIRST-PARTY AND VALIDATED, AND THE ACCEPT-LIST IS EXACTLY THREE TIERS. Z.ai's
Anthropic-compatible endpoint serves glm-5.3-flash on this key today (it 429'd two days ago, which
is why the row was missing), and it validates output_config.effort against a closed enum: low,
high and max return HTTP 200, and none, minimal, medium, xhigh and an invented bogus_zzz are all
REJECTED HTTP 400 code 1210. A bad model id is rejected separately with code 1211, so the 400 on a
bad effort is about the effort field and not about a malformed request in general. That is the
strongest signature this board accepts short of a measured magnitude: an endpoint that rejects
everything outside its list is not silently clamping the values inside it.

    output_config.effort   glm-5.3-flash    glm-5.3
    none                   400  [1210]      400  [1210]
    minimal                400  [1210]      400  [1210]
    low                    200              200
    medium                 400  [1210]      400  [1210]
    high                   200              200
    xhigh                  400  [1210]      400  [1210]
    max                    200              200
    bogus_zzz              400  [1210]      400  [1210]  "reasoning_effort must be one of:
                                                          none, minimal, low, medium, high,
                                                          xhigh, max"
    (model id glm-5.3-flash-zzz)            400  [1211]  "Unknown Model, please check the
                                                          model code"

    rejection text on every 400/1210:
    "This model always engages in thinking and cannot be disabled; please use low, high, or max"

Identical on both sizes, probed in the same session on the same key within four minutes. So the
dial on this family is low | high | max and nothing else - the three tiers Z.ai documents - and the
gateway treats every other Anthropic tier as a request to turn thinking off, which this family does
not permit. THAT KILLS ONE OF THE TWO FOLLOW-UPS BEFORE IT COSTS ANYTHING: a `medium` row on this
path is not available to be run. The dial that IS available is three points, low / high / max.

*** I NEARLY PUBLISHED THE OPPOSITE, AND THE NEAR-MISS IS THE MOST USEFUL THING HERE ***

The first pass of this probe sent `reasoning_effort` at the top level of the request - the field
name Z.ai's own OpenAI-compatible documentation uses. Every tier returned HTTP 200, including
bogus_zzz, while the bad model id returned 400. That is textbook: an endpoint that 200s an invented
tier is not reading the field, so the tier is inert. The verdict written automatically was "NOT
VALIDATED - TREAT AS INERT", and a row shipped on it would have been labelled inert_default and
would have said the dial does not bind here.

It was wrong because Claude Code does not send that field. On an Anthropic-compatible route it
sends `output_config.effort` (measured on the wire, 20260912-claude-code-wire-default-effort.txt),
and output_config is what this endpoint validates. Top-level reasoning_effort is simply an unknown
key and is ignored - which is why it "accepted" bogus_zzz.

The rule that falls out of it, and it generalises past Z.ai: a validation probe has to send THE
FIELD THE HARNESS SENDS. Probing the vendor's documented field name rather than the one on the
actual wire tests a path the arm will never take, and the answer it gives is about that path. The
tell that something was wrong was in the receipt already: the 2026-09-10 pass recorded a rejection
naming "none, minimal, low, medium, high, xhigh, max" - which is ANTHROPIC's enum, not Z.ai's
documented low|high|max - so the validated field had to be the Anthropic-shaped one.

WHY THE ROW WAS MISSING, which is the question that prompted this. GLM-5.3 Flash has exactly one
row on this board and it ran through OpenRouter, where the effort field is dropped in transit, so
its effort column is a request rather than a setting. The 2026-09-10 first-party pass that fixed
precisely that for the full-size GLM-5.3 TRIED Flash first and could not use it: glm-5.3-flash
returned 429 on this key, and a 429 proves nothing about a dial, so the receipt was written against
glm-5.3 and Flash stayed where it was. The 429 is gone today. Nothing was overlooked; the endpoint
would not answer.

WHAT THIS LICENSES. An arm on this path may assert a tier, and effort_status is first_party - the
same status the glm53zaimax row carries, on the same endpoint, for the same reason. It is NOT
`verified`: nothing here measures whether low, high and max produce different behaviour, only that
the endpoint reads the field and refuses what it does not recognise. A magnitude claim needs the
three-point run, which is the planned follow-up, minus the medium leg that does not exist.

ONE THING TO CARRY INTO THAT FOLLOW-UP. Z.ai documents max as the DEFAULT for this family, so a
`default` run and a `max` run on this path are the same run. The low and high legs are where the
dial's shape would actually show.
